# Limpieza Timer Synchronization Bugfix Design

## Overview

The cleaning timer in the limpieza page has a synchronization issue where client-side optimistic timing uses `Date.now()` while the server records timestamps from the database server's clock. This causes timer desynchronization when pages are refreshed, showing different elapsed times between client calculation and server-recorded start time. The fix will ensure consistent timestamp usage while preserving the immediate visual feedback users expect when starting a cleaning session.

## Glossary

- **Bug_Condition (C)**: The condition that triggers the bug - when client-side timer uses different timestamp source than server-side database storage
- **Property (P)**: The desired behavior - single authoritative timestamp source used consistently for both client display and server persistence
- **Preservation**: Existing immediate visual feedback, real-time timer updates, and accurate duration calculation that must remain unchanged by the fix
- **handleStartCleaning()**: The function in `app/limpieza/page.tsx` that initiates cleaning sessions and manages timer synchronization
- **Date.now()**: Client-side JavaScript method that returns milliseconds since epoch using local machine time
- **optimisticStartMs**: Local timestamp generated by `Date.now()` for immediate visual feedback
- **iniciado_at**: Database timestamp stored in `ciclos_limpieza` table recording when cleaning started
- **cleaningStarts**: Client-side state mapping room IDs to start times in milliseconds UTC epoch

## Bug Details

### Bug Condition

The bug manifests when a user clicks "Iniciar Limpieza" to start cleaning a room. The `handleStartCleaning()` function generates an optimistic local timestamp using `Date.now()` for immediate visual feedback, but persists a potentially different timestamp to the database. When the page refreshes and fetches from the `ciclos_limpieza` table, the server timestamp may differ from the client's `Date.now()` due to clock differences, causing timer desynchronization.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type CleaningStartEvent
  OUTPUT: boolean
  
  RETURN input.clientGeneratedTimestamp != input.serverRecordedTimestamp
         AND input.usesClientClockForDisplay = true
         AND input.usesServerClockForStorage = true
END FUNCTION
```

### Examples

- **Example 1**: Client clock shows 10:00:00 AM, server clock shows 10:00:05 AM. User starts cleaning at client time 10:00:00, DB records 10:00:05. After 30 seconds, client timer shows 00:30, but DB elapsed time would be 00:25.
- **Example 2**: Client clock is 2 minutes ahead of server. User starts cleaning, client shows 00:00, DB records time 2 minutes earlier. On refresh, timer jumps forward 2 minutes.
- **Example 3**: Client clock drifts over time. Cleaning starts with small difference, but after several minutes, discrepancy grows noticeable.
- **Edge Case**: Network latency causes delay between client timestamp generation and server recording, exacerbating the difference.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Immediate visual feedback when "Iniciar Limpieza" is clicked - timer must start without noticeable delay
- Real-time elapsed time updates every second during cleaning sessions
- Accurate duration calculation when cleaning sessions end
- Concurrent cleaning session handling for multiple users
- Timer display with progress bars and SLA tracking

**Scope:**
All functionality not directly related to timestamp synchronization should be completely unaffected by this fix. This includes:
- Button click handling and UI state transitions
- Progress bar visualization and color coding based on elapsed time
- SLA violation detection and webhook notifications
- Room filtering, zoning, and prioritization features
- Real-time updates via Supabase subscriptions

## Hypothesized Root Cause

Based on the bug description and code analysis, the most likely issues are:

1. **Clock Source Inconsistency**: The function uses `Date.now()` for client display but relies on database server timestamp for persistence
   - Client machine time may differ from server time by seconds or minutes
   - No synchronization mechanism between client and server clocks

2. **Optimistic Update Pattern**: Immediate visual feedback requires local timestamp generation
   - Current implementation prioritizes user experience over timestamp consistency
   - No mechanism to synchronize optimistic timestamp with authoritative source

3. **Network Latency Gap**: Time between client timestamp generation and server recording
   - Even with synchronized clocks, network delay creates discrepancy
   - No compensation for request/response latency

4. **Refresh Discrepancy**: On page refresh, timer recalculates from database timestamp
   - Client loses local optimistic timestamp on refresh
   - Must rely on potentially different server timestamp

## Correctness Properties

Property 1: Bug Condition - Single Authoritative Timestamp

_For any_ input where the bug condition holds (isBugCondition returns true), the fixed `handleStartCleaning` function SHALL use a single authoritative timestamp source consistently for both client display and server persistence, eliminating timer desynchronization.

**Validates: Requirements 2.1, 2.2, 2.3**

Property 2: Preservation - Immediate Visual Feedback

_For any_ input where the bug condition does NOT hold (isBugCondition returns false), the fixed function SHALL produce the same immediate visual feedback as the original function, preserving the user experience of instant timer start without noticeable delay.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4**

## Fix Implementation

### Changes Required

Assuming our root cause analysis is correct:

**File**: `app/limpieza/page.tsx`

**Function**: `handleStartCleaning()`

**Specific Changes**:
1. **Server Timestamp Retrieval**: Before optimistic update, fetch current server timestamp via API
   - Create API endpoint that returns current server time
   - Use this timestamp for both optimistic update and database storage
   - Implement fallback to client time if server fetch fails

2. **Timestamp Synchronization**: Ensure same timestamp used for client state and database
   - Replace `Date.now()` with server timestamp for `optimisticStartMs`
   - Use same timestamp for `iniciado_at` in database upsert
   - Store authoritative timestamp in `cleaningStarts` state

3. **Network Latency Compensation**: Account for round-trip time to server
   - Measure time between request initiation and response receipt
   - Adjust client display if significant latency detected
   - Implement retry logic for timestamp fetch failures

4. **Fallback Mechanism**: Maintain functionality if server timestamp unavailable
   - Use client timestamp with warning/notification
   - Log discrepancies for monitoring and debugging
   - Allow manual timestamp correction if needed

5. **State Management Updates**: Modify `cleaningStarts` state handling
   - Store server-authoritative timestamps instead of client-generated ones
   - Update real-time subscription to use server timestamps
   - Ensure timer calculations use consistent timestamp source

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Write tests that simulate cleaning start with controlled clock differences between client and server. Run these tests on the UNFIXED code to observe timer discrepancies and understand the root cause.

**Test Cases**:
1. **Clock Difference Test**: Simulate client clock 30 seconds ahead of server (will fail on unfixed code)
2. **Network Latency Test**: Add 2-second delay between client timestamp and server recording (will fail on unfixed code)
3. **Refresh Discrepancy Test**: Start cleaning, simulate page refresh, compare elapsed times (will fail on unfixed code)
4. **Edge Case Test**: Client clock drifting during long cleaning session (may fail on unfixed code)

**Expected Counterexamples**:
- Timer shows different elapsed time after page refresh compared to before refresh
- SLA violations triggered at wrong times due to timestamp discrepancies
- Possible causes: clock inconsistency, network latency, no timestamp synchronization

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds, the fixed function produces the expected behavior.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := handleStartCleaning_fixed(input)
  ASSERT result.usesSingleTimestampSource = true
  ASSERT result.clientDisplayTime = result.serverStorageTime
  ASSERT result.timerConsistentAfterRefresh = true
END FOR
```

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT handleStartCleaning_original(input).immediateFeedback = 
         handleStartCleaning_fixed(input).immediateFeedback
  ASSERT handleStartCleaning_original(input).realTimeUpdates = 
         handleStartCleaning_fixed(input).realTimeUpdates
  ASSERT handleStartCleaning_original(input).durationAccuracy = 
         handleStartCleaning_fixed(input).durationAccuracy
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many test cases automatically across the input domain
- It catches edge cases that manual unit tests might miss
- It provides strong guarantees that behavior is unchanged for all non-buggy inputs

**Test Plan**: Observe behavior on UNFIXED code first for immediate feedback and timer updates, then write property-based tests capturing that behavior.

**Test Cases**:
1. **Immediate Feedback Preservation**: Verify timer starts within 100ms of button click on unfixed code, then test continues after fix
2. **Real-time Updates Preservation**: Verify timer updates every second accurately on unfixed code, then test continues after fix
3. **Concurrent Sessions Preservation**: Verify multiple users can clean different rooms simultaneously on unfixed code, then test continues after fix
4. **SLA Tracking Preservation**: Verify SLA violations detected correctly based on elapsed time on unfixed code, then test continues after fix
