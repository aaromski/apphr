# Bugfix Requirements Document

## Introduction

The cleaning timer in the limpieza page suffers from a synchronization issue between client-side optimistic timing and server-side database timing. When a user initiates cleaning by clicking "Iniciar Limpieza", the timer starts immediately on the client-side using `Date.now()`, but the server records a different timestamp in the database due to clock differences between client and server. This causes a desynchronization where the displayed timer duration doesn't match the actual database-recorded duration when the page is refreshed.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN a user clicks "Iniciar Limpieza" to start cleaning a room THEN the system immediately starts a client-side timer using local machine time (`Date.now()`)
1.2 WHEN the system persists the cleaning start time to the database THEN it records the server's current timestamp which may differ from the client's timestamp
1.3 WHEN the page is refreshed and the timer fetches data from the database THEN the displayed elapsed time shows a discrepancy between client-side calculation and server-recorded start time

### Expected Behavior (Correct)

2.1 WHEN a user clicks "Iniciar Limpieza" to start cleaning a room THEN the system SHALL use a single authoritative timestamp source for timer calculation
2.2 WHEN the system persists the cleaning start time THEN it SHALL use the same timestamp that will be used for client-side timer calculations
2.3 WHEN the page is refreshed and fetches timer data THEN the displayed elapsed time SHALL be calculated consistently using the same timestamp source as the initial timer start

### Unchanged Behavior (Regression Prevention)

3.1 WHEN the "Iniciar Limpieza" button is clicked THEN the system SHALL CONTINUE TO provide immediate visual feedback with timer starting without noticeable delay
3.2 WHEN cleaning is in progress THEN the system SHALL CONTINUE TO display real-time elapsed time updates every second
3.3 WHEN the cleaning session ends THEN the system SHALL CONTINUE TO calculate and record the total duration accurately
3.4 WHEN multiple users access the cleaning interface THEN the system SHALL CONTINUE TO handle concurrent cleaning sessions correctly


## Bug Condition and Property Specifications

### Bug Condition Function

The bug occurs when the cleaning timer uses different timestamp sources for client-side display and server-side persistence.

```pascal
FUNCTION isBugCondition(X)
  INPUT: X of type CleaningStartEvent
  OUTPUT: boolean
  
  // Returns true when client and server timestamps differ
  RETURN X.clientTimestamp ≠ X.serverTimestamp
END FUNCTION
```

Where:
- `CleaningStartEvent` represents the event of starting a cleaning session
- `clientTimestamp` is the timestamp generated by `Date.now()` on the client
- `serverTimestamp` is the timestamp recorded in the database by the server

### Property Specification

**Property: Fix Checking** - Ensures consistent timestamp usage

```pascal
// Property: Fix Checking - Single Authoritative Timestamp
FOR ALL X WHERE isBugCondition(X) DO
  result ← F'(X)
  ASSERT result.usesSingleTimestampSource = true
END FOR
```

**Property: Preservation Checking** - Ensures non-buggy behavior remains unchanged

```pascal
// Property: Preservation Checking - Immediate Visual Feedback
FOR ALL X WHERE NOT isBugCondition(X) DO
  ASSERT F(X).immediateVisualFeedback = F'(X).immediateVisualFeedback
END FOR
```

### Key Definitions

| Concept | Definition | Example |
|---------|------------|---------|
| **C(X)** | Bug Condition - client and server timestamps differ | `clientTimestamp ≠ serverTimestamp` |
| **P(result)** | Property - uses single authoritative timestamp source | `usesSingleTimestampSource = true` |
| **¬C(X)** | Non-buggy inputs - timestamps are synchronized | `clientTimestamp = serverTimestamp` |
| **F** | Original (unfixed) function - uses `Date.now()` for client, server time for DB | Current implementation with optimistic timer |
| **F'** | Fixed function - uses single authoritative timestamp source | Fixed implementation with synchronized timing |
| **Counterexample** | Concrete example demonstrating the bug | Timer shows 1:30 elapsed, DB shows 1:25 elapsed after refresh |

### Derived Requirements

From the bug condition, we derive the following implementation requirements:

1. **Single Timestamp Source**: Either use server timestamp for both client and server, or use client timestamp consistently propagated to server
2. **Immediate Feedback Preservation**: The fix must maintain the current user experience of immediate timer start
3. **Clock Synchronization**: Address potential clock drift between client and server systems
4. **Network Latency Handling**: Account for network delay in timestamp propagation

The recommended fix is to use server-generated timestamps for both client display and database storage, with client-side optimistic updates synchronized to server time.
